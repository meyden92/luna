# MariaDB to PostgreSQL type and semantics mapping

Sources read directly: `prisma/migrations/20260214202500_baseline_db_as_is/migration.sql` (660 lines, baseline DDL), all 15 later migrations in `prisma/migrations/*/migration.sql`, and `prisma/schema.prisma` (803 lines, 38 models). The baseline DDL is a snapshot; the *current* schema is the baseline plus all 15 later migrations applied — that cumulative state is what this document maps, since it's what actually needs to become Drizzle+Postgres DDL. Two tables from the baseline (`permission_definition`, `rbac_group_inheritance`) and one column set (`rbac_group_permission.pattern`/`effect` ENUM) were dropped in `20260217120000_simplify_admin_groups`; the `apikey` table was dropped and replaced by `token` in `20260311143533_simplify_api_key`. Both are noted below but excluded from "current" counts.

## Answer in brief

- **Highest risk, not behaviour-preserving: collation/case-sensitivity.** MariaDB's default collation is `utf8mb4_unicode_ci` (case-insensitive) on every table. Postgres `text`/`varchar` comparison is case-sensitive by default. All `contains:` (LIKE) searches in the codebase — file title/tag search, admin user search, audit log search, task search — and the denylist-hash exact-match moderation gate will silently change behavior with **zero code-level errors**. See Q6 for concrete file:line sites.
- **Not behaviour-preserving: `json` type semantics under MariaDB are not what they appear.** MariaDB's `JSON` is a `LONGTEXT` alias with a `JSON_VALID()` CHECK constraint, not a real structured type — no key-order/whitespace normalization happens on write. Moving to Postgres `jsonb` (recommended) normalizes key order, drops whitespace, and collapses duplicate keys on write. For the app's use (structured data payloads, not raw-text diffing) this is safe, but it is not byte-identical.
- **Not behaviour-preserving (ORM-migration-induced, not DB-induced): `Prisma.DbNull`.** All 9 usages in `src/libs/prismadb.ts` are `Prisma.DbNull` (never `JsonNull`); Drizzle has no DbNull/JsonNull distinction — passing plain `null` in Drizzle happens to reproduce `DbNull` semantics exactly, so this is fixable but must be done deliberately, not by naive find-replace.
- **Not behaviour-preserving: booleans stored as `TINYINT(1)` in MariaDB accept any integer** (truthy/falsy), while Postgres `boolean` only accepts true/false-coercible literals. No risk found through Prisma (it always surfaces JS `boolean`), but any future raw SQL touching these columns will behave differently.
- **Partially not behaviour-preserving: string ordering (`ORDER BY`).** MariaDB's Unicode collation sort order will not exactly match whatever Postgres locale/collation the new cluster uses; this needs an explicit decision (see Q6), not a default assumption.
- Auto-increment integer PKs are **not used at all** — every ID is an application-generated UUID string (`crypto.randomUUID()` or `@default(uuid())`). Identity/serial columns are not needed anywhere in this schema (Q7).
- The only identifier collision found is the `user` table name, which is a **reserved word** in Postgres and must be quoted (`"user"`) everywhere in raw SQL (Q8) — Drizzle handles this automatically, but it's a footgun for any hand-written SQL or psql access.
- `VARCHAR(191)` and the two prefix-length indexes (`apikey_key_idx`, `verification_identifier_idx`) are MySQL/MariaDB-InnoDB-specific artifacts of the historic 767-byte index-key limit under `utf8mb4`; Postgres has no equivalent limit for a `text`/`varchar` column of this size, so the constraint disappears and the index can — and should — be a plain full-column index (Q5).
- Everything else (integers, doubles, bigints, datetimes-as-values, foreign key `ON DELETE`/`ON UPDATE` actions, plain text/varchar storage) maps cleanly and is behaviour-preserving.

## 2. Json columns (28 in the current schema.prisma, not 29)

`grep -n "Json" prisma/schema.prisma` returns 29 lines, but one (line 597) is a comment (`// Result image URLs live in \`result\` (Json) ...`) referencing a field already counted, not a distinct column. The actual count of `Json`/`Json?` columns is **28**: `File.scrubReport`, `FileRendition.params`, `ModerationCase.uploadMetadata`, `Flow.graph`, `FlowRun.items`, `FlowRun.logs`, `ViewDailyRollup.referrerBreakdown`/`countryBreakdown`/`deviceBreakdown`, `OCRResult.words`/`lines`/`statistics`, `AuditLog.before`/`after`/`metadata`/`fieldChanges`, `Task.args`, `TaskExecution.result`/`logs`, `Template.variables`/`editingModelFieldValues`, `GlobalVariable.options`, `TemplateGlobalVariable.addedOptions`, `TemplateGeneration.variableValues`/`originalImageUrls`, `AiGeneration.inputImageUrls`/`result`, `ImagePreset.fieldValues`.

**json vs jsonb — recommend `jsonb`.** Per the official Postgres docs (postgresql.org/docs/current/datatype-json.html):
- `json` "stores an exact copy of the input text ... preserve[s] semantically-insignificant white space ... and the order of keys ... if a JSON object ... contains the same key more than once, all the key/value pairs are kept."
- `jsonb` "does not preserve white space, does not preserve the order of object keys, and does not keep duplicate object keys. If duplicate keys are specified in the input, only the last value is kept."
- Only `jsonb` supports indexing (GIN, btree, hash) and the containment/existence operators (`@>`, `?`, `@?`, `@@`).
- Postgres' own recommendation: "most applications should prefer to store JSON data as `jsonb`, unless there are quite specialized needs, such as legacy assumptions about ordering of object keys."

None of the 28 columns in this schema depend on key order or duplicate keys being preserved — they are structured payloads (audit snapshots, task args, generation results, form field maps) consumed programmatically, not diffed as raw text. `jsonb` is the right choice, and it gains queryability (e.g. `audit_log.metadata`, `moderation_case.uploadMetadata`) that the app doesn't currently use but may want.

**MariaDB's `JSON` is not a real structured type.** Per MariaDB's own docs (mariadb.com/kb/en/json-data-type/): "JSON is an alias for LONGTEXT COLLATE utf8mb4_bin introduced for compatibility reasons with MySQL's JSON data type," and "This constraint is automatically included for types using the JSON alias" (a `JSON_VALID()` CHECK). This explains why some of the earlier-created columns in this repo's baseline DDL (e.g. `audit_log.before`/`after`/`metadata`/`fieldChanges`, `task.args`, `template.variables`) are literally typed `LONGTEXT` in the raw SQL rather than `JSON` — they predate the DDL using Prisma's `Json` scalar consistently, but under MariaDB the two are functionally identical (both are `LONGTEXT` + optional validity check). The later migrations (`20260617152501_add_ai_generation_and_image_preset` onward) do use the `JSON` keyword directly. Either way, moving to Postgres `jsonb` is a real upgrade, not a downgrade, in every one of these cases.

**`Prisma.DbNull` / `Prisma.JsonNull` — the actual code.** All 9 usages are in `src/libs/prismadb.ts` (the audit-log extension), and every single one is `Prisma.DbNull` — `JsonNull` is never used anywhere in `src`:
```
src/libs/prismadb.ts:153   after: Prisma.DbNull,
src/libs/prismadb.ts:154   metadata: metadata || Prisma.DbNull,
src/libs/prismadb.ts:157   fieldChanges: Prisma.DbNull,
src/libs/prismadb.ts:177   metadata: metadata || Prisma.DbNull,
src/libs/prismadb.ts:180   fieldChanges: diffResult.hasChanges ? diffResult.changes : Prisma.DbNull,
src/libs/prismadb.ts:198   before: before ? JSON.parse(JSON.stringify(before)) : Prisma.DbNull,
src/libs/prismadb.ts:199   after: after ? JSON.parse(JSON.stringify(after)) : Prisma.DbNull,
src/libs/prismadb.ts:200   metadata: metadata || Prisma.DbNull,
src/libs/prismadb.ts:203   fieldChanges: diffResult.hasChanges ? diffResult.changes : Prisma.DbNull,
```
Per Prisma's own docs (prisma.io/docs/orm/prisma-client/special-fields-and-types/working-with-json-fields): `JsonNull` "represents the `null` value in JSON" (the column has a value, and that value is the JSON scalar `null`); `DbNull` "represents the `NULL` value in the database" (the column itself is empty/SQL NULL); `AnyNull` matches either, for filtering only. Prisma requires this explicit choice for nullable `Json` fields because a bare JS `null` is ambiguous between the two on a relational backend — this distinction is identical for the MySQL and Postgres Prisma providers, so it is **not** a MariaDB-vs-Postgres difference; it's a Prisma-specific modeling concern.

**What Drizzle does not model, and what breaks.** Per Drizzle's own column-types docs (orm.drizzle.team/docs/column-types), Drizzle's `json()`/`jsonb()` builders have no DbNull/JsonNull-equivalent sentinel — you pass a plain JS value or `null`, and Drizzle always writes SQL NULL for `null`. Because 100% of this codebase's usages are `DbNull` (never `JsonNull`), a literal port of `Prisma.DbNull → null` in the Drizzle rewrite is behaviour-preserving here. The risk is not this migration specifically, but the class of bug it invites: if a future Drizzle write needs "store the JSON value `null`" (there is no current example of this in `src`), a naive `null` will silently become a `DbNull` instead of a `JsonNull` unless the code explicitly writes something like `sql\`'null'::jsonb\``. Flag this as a review item for the Drizzle rewrite PR, not a blocker for this schema as it stands today.

## 3. Booleans

MariaDB DDL declares every boolean column as `BOOLEAN` (e.g. `apikey.enabled`, `file.private`, `user.active`, `user.isDeleted`, `session`/`account` don't have any, `task.enabled`, etc.). Per MariaDB's docs (mariadb.com/kb/en/boolean/): "BOOLEAN and BOOL are synonyms for TINYINT(1)"; "A value of zero is considered false. Non-zero values are considered true"; "The values TRUE and FALSE are merely aliases for 1 and 0." This means the underlying column genuinely accepts any signed 8-bit integer, not just 0/1, at the storage layer.

Postgres `boolean` is a true 1-byte boolean type that only accepts boolean literals or coercible strings (`'t'`/`'f'`, `'true'`/`'false'`, `'1'`/`'0'`, etc.) — it rejects arbitrary integers outright.

**Code-level risk: none found.** Every boolean field is read/written exclusively through Prisma, which always surfaces the MySQL/MariaDB `TINYINT(1)` as a JS `boolean` — the app never sees a raw 0/1. The `=== 0` / `=== 1` comparisons found in `src` (`platform.ts:315`, various date/loop-index checks) are all against numbers unrelated to boolean columns, not against boolean fields. **Conclusion:** behaviour-preserving through the ORM layer; would only break if a future raw `$queryRaw`/`sql` call assumed a boolean column could hold values other than 0/1 (no such call exists today).

## 4. Date/time

Every timestamp column in the DDL is `DATETIME(3)` (millisecond precision), used for: `createdAt`/`updatedAt` (near-universal), soft-delete `deletedAt`, business timestamps (`expiresAt`, `lastAccessedAt`, `occurredAt`, `startedAt`/`completedAt`, `resolvedAt`, `lastExecutionAt`/`nextExecutionAt`, `banExpires`).

**Defaults and `ON UPDATE`:** `createdAt`-style columns use `DEFAULT CURRENT_TIMESTAMP(3)` at the DB level (present in the DDL for every table). Critically, **`updatedAt` columns have no `DEFAULT` and no `ON UPDATE CURRENT_TIMESTAMP(3)` clause anywhere in any of the 16 migration files** — e.g. `account.updatedAt DATETIME(3) NOT NULL` with nothing else. This proves `@updatedAt` is enforced entirely by Prisma Client at the query level (it stamps the value into every `UPDATE`/`CREATE` it issues), not by MariaDB automation. **Consequence for the Drizzle port:** there is no MySQL `ON UPDATE CURRENT_TIMESTAMP` to replace — this was already an application-level concern. Drizzle's equivalent is `$onUpdate(() => new Date())` (or explicit assignment in every update call), which reproduces the exact same behaviour Prisma already had. This is genuinely behaviour-preserving, not a gap.

**`timestamp` vs `timestamptz` — recommend `timestamptz`.** Per Postgres docs (postgresql.org/docs/current/datatype-datetime.html): `timestamp without time zone` "will silently ignore any time zone indication ... the resulting value is derived from the date/time fields in the input string, and is not adjusted for time zone," while `timestamp with time zone` values are "stored internally in UTC" and "converted to local time in the zone specified by the TimeZone configuration parameter before being displayed." MariaDB `DATETIME` behaves like Postgres `timestamp` (no timezone attached, literal wall-clock storage). The app treats all timestamps as UTC — `docker-compose.yml` sets `TZ=UTC` on the app container, and `src/server/fns/admin/tasks.ts:149` explicitly falls back through `process.env.TZ || Intl.DateTimeFormat().resolvedOptions().timeZone || 'UTC'` when resolving a cron display timezone. No code was found doing timezone-offset math on these DB timestamps beyond that one display-formatting site. Given that, `timestamptz` with the Postgres session `TimeZone` pinned to `UTC` reproduces the current behaviour exactly (values round-trip identically) and additionally protects against a future deploy where the app or a client connects with a non-UTC session timezone — `timestamp` would silently misinterpret such a connection, `timestamptz` would not. This requires the Postgres cluster's `TimeZone` GUC (or at minimum every application connection) to be explicitly set to UTC; if that setup step is skipped, `timestamptz` is not automatically behaviour-preserving.

**MySQL zero-dates:** not found in any migration or seed data in this repo (`grep` for `0000-00-00` across all migration files returned nothing), and every `DATETIME` column here is either `NOT NULL` with a real default or nullable — there's no code path shown creating a zero-date. **Unverified:** whether the live MariaDB server's `sql_mode` includes `NO_ZERO_DATE`/`NO_ZERO_IN_DATE` is not stored in this repo and can't be confirmed from source alone; if it's absent, zero-dates could theoretically exist in production data despite the schema not implying them.

## 5. Strings and indexes

`@db.Text` maps to MariaDB `TEXT`/`LONGTEXT` depending on the field (Prisma's default `@db.Text` on MySQL is `TEXT`; several older columns are `LONGTEXT` from before the schema consistently declared `@db.Text`/`Json`). Both map to Postgres `text` (Q1 table).

`varchar(191)` and the two prefix-length indexes:
```
INDEX `apikey_key_idx`(`key`(191) ASC)                    -- baseline DDL, migration.sql:47 (table later dropped)
INDEX `verification_identifier_idx`(`identifier`(191) ASC) -- baseline DDL, migration.sql:559 (still current)
```
Both index on a `TEXT` column with a `(191)` prefix length, not a `VARCHAR(191)` column itself — a `TEXT` column can't be indexed directly in InnoDB without a prefix length. **Why 191:** per the MySQL/InnoDB reference manual (dev.mysql.com/doc/refman/8.0/en/innodb-limits.html, describing the same InnoDB engine MariaDB is built on) and MariaDB's own row-formats docs (mariadb.com/kb/en/innodb-row-formats-overview/, which states the "Maximum size of indexed column values" is 767 bytes for `REDUNDANT`/`COMPACT` row format): "The index key prefix length limit is 767 bytes for InnoDB tables that use the REDUNDANT or COMPACT row format. For example, you might hit this limit with a column prefix index of more than 191 characters on a TEXT or VARCHAR column, assuming a utf8mb4 character set and the maximum of 4 bytes for each character." 767 ÷ 4 = 191.75, floored to 191. This is a historical MySQL/MariaDB InnoDB-page-format artifact — Prisma's MySQL provider defaults every unannotated `String @id`/indexed `String` to `VARCHAR(191)` specifically to stay under this limit regardless of row format.

**Why it vanishes on Postgres:** Postgres has no analogous fixed 767-byte prefix-index ceiling tied to character set width; `text`/`varchar` columns of this length index without any prefix truncation. **Recommendation:** for the Drizzle/Postgres port, index `verification.identifier` and (historically) `apikey.key` on the full column value — `CREATE INDEX ... ON verification (identifier)` — rather than reproducing a prefix index. A full-column index is strictly more correct (a prefix index can produce false-positive index hits requiring a recheck against the full value, and to duplicate the old semantics exactly one would need `substring(identifier, 1, 191)`, which is unnecessary complexity carried over from a constraint that no longer applies).

## 6. Collation and case sensitivity — highest risk

**Confirmed collation in the DDL:** every single `CREATE TABLE` statement across all 16 migration files that specifies a table option ends with `DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`. The `_ci` suffix means case-insensitive comparison (per MariaDB's collation naming convention, mariadb.com/kb/en/setting-character-sets-and-collations/). The 8 tables created in the final migration (`20260701120000_selected_findings_features`: `file_rendition`, `denylist_entry`, `moderation_case`, `flow`, `flow_run`, `view_event`, `view_daily_rollup`, `egress_event`, `egress_rollup`) omit the explicit `DEFAULT CHARACTER SET ...` clause in their `CREATE TABLE` statements — they inherit the database's default charset/collation. **Unverified:** the database-level default charset/collation is not declared anywhere in this repo (no `CREATE DATABASE` statement, no MariaDB server config file); given every other table explicitly sets `utf8mb4_unicode_ci` and Prisma/MariaDB commonly defaults new databases the same way as the connection default, it's a reasonable assumption these 8 tables also end up `utf8mb4_unicode_ci`, but this is not confirmed from source and should be checked against the live server before cutover.

Postgres `text`/`varchar` comparison is case-sensitive (and, per postgresql.org/docs/current/functions-matching.html, `LIKE` is explicitly case-sensitive — "The key word ILIKE can be used instead of LIKE to make the match case-insensitive" — `ILIKE` is required for a case-insensitive match). Prisma's `contains:`/`startsWith:` filters translate to `LIKE` on both providers, but under MySQL's ci collation `LIKE` is already case-insensitive by default, so the app never needed Prisma's `mode: 'insensitive'` option. **`grep -rn "mode:\s*['\"]insensitive" src` returns zero matches anywhere in the codebase.**

Concrete, currently-case-insensitive lookups that will silently start behaving differently:

- **Free-text search (case-insensitive → case-sensitive, breaks UX silently):**
  - `src/server/fns/files.ts:168` — `{ OR: [{ title: { contains: searchValue } }, { tags: { contains: searchValue } }] }` (file/gallery search box)
  - `src/server/fns/files.ts:192` — `{ tags: { contains: tag.trim() } }` (tag filter)
  - `src/server/fns/admin/users.ts:152` — `{ OR: [{ email: { contains: search } }, { name: { contains: search } }] }` (admin user search)
  - `src/server/fns/admin/audit.ts:90-94` — `model`/`recordId`/`action`/`user.name`/`user.email` search in the audit log viewer
  - `src/server/fns/admin/tasks.ts:388` — `{ task: { name: { contains: data.search } } }` / `{ error: { contains: data.search } }` (task execution search)
- **Exact-equality security lookups (case-insensitive → case-sensitive, a *behaviour improvement that must be reviewed, not assumed safe*):**
  - `src/libs/auth/token-auth.ts:8-18` (`validateTokenKey`) — `prisma.token.findFirst({ where: { key, enabled: true, ... } })`. Under MariaDB's ci collation, a token key is currently matched case-insensitively; on Postgres it becomes exact-case. This tightens security (good) but is a real behaviour change for any client sending a differently-cased key today.
  - `src/libs/moderation/hash-gate.ts:37-41` (`findDenylistMatchForHashes`) — `{ hashType: 'sha256', hash: hashes.sha256 }` / `{ hashType: 'md5', hash: hashes.md5 }`. The app always computes lowercase hex digests (Node `crypto...digest('hex')` is always lowercase), so this is low-risk *for hashes the app itself generates* — but `denylist_entry` rows can be manually inserted (e.g. from an external threat-intel/PhotoDNA-style list, which commonly ships uppercase hex). Under MariaDB, a denylist entry entered in any case still matches; under Postgres, a case mismatch means a denylisted file **silently passes the moderation gate**. This is the single highest-severity finding in this document.
  - `src/libs/rbac/default-group.ts:31-34,64-67` — `rbacGroup.findUnique({ where: { key } })` against the fixed literals `'user'`/`'admin'` (`USER_GROUP_KEY`/`ADMIN_GROUP_KEY`). Both sides are always-lowercase compile-time constants, so this specific site is low-risk in practice, but it depends on that invariant never changing.
  - `user.email` uniqueness (`user_email_key`) and the better-auth login lookup: no email-normalization (`.toLowerCase()`) was found anywhere in `src/libs/auth/`. Under MariaDB ci collation, `User@Example.com` and `user@example.com` collide (one registration, case-insensitive login). Under Postgres, they become two distinct rows and two distinct accounts — a functional change to signup/login, and a duplicate-account risk if the app doesn't add explicit normalization before cutover.
- **`ORDER BY` on string columns:** `src/server/fns/admin/templates.ts:112,136`, `src/server/fns/admin/global-variables.ts:10`, `src/server/fns/admin/users.ts:78` all `orderBy: { name: 'asc' }`. MariaDB's Unicode collation sort order will not necessarily match whatever Postgres locale/collation the target cluster uses (this depends entirely on how the Postgres database is `initdb`'d — not yet decided, see Open questions). This is a cosmetic risk (list ordering), not a correctness one, but it is silent.

**Remedy options and trade-offs:**
1. **`citext` extension** (postgresql.org/docs/current/citext.html) — case-insensitive type, drop-in for `email`/`key`/`hash` columns that must reproduce today's exact behaviour. Pros: transparent, works for unique constraints and `=`/`LIKE`/`~~` without query changes. Cons (from the docs): "citext's case-folding behavior depends on the LC_CTYPE setting of your database" (locale-dependent, "not truly case-insensitive in the terms defined by the Unicode standard"); "citext is not as efficient as text ... only text can support B-Tree deduplication"; the docs themselves suggest nondeterministic collations as a more modern alternative.
2. **`lower()` + functional index, explicit `mode: 'insensitive'`-equivalent in query code** — most explicit and auditable; requires touching every query site listed above and adding a matching expression index (e.g. `CREATE INDEX ON user (lower(email))`). No new extension dependency. More code churn but zero magic.
3. **`COLLATE` (deterministic/nondeterministic case-insensitive collation on the column)** — Postgres 12+ supports custom ICU collations; a nondeterministic case-insensitive collation applied at the column level reproduces MariaDB-like behaviour without an extension, per Postgres' own recommendation over `citext`. Newest option, least prior art in this codebase's stack, but the one Postgres itself now points to as preferred.

**Recommendation:** treat this as a per-column decision, not a blanket policy — `citext` (or a case-insensitive collation) for `user.email` and `token.key` (things that are semantically identifiers people type inconsistently), explicit `lower()`/`ILIKE` at the query sites for the free-text search fields (search UX doesn't need a schema-level guarantee), and a deliberate decision — not a default — for `denylist_entry.hash` given the security stakes identified above.

## 7. Identity / auto-increment

**No column in this schema is MySQL/MariaDB `AUTO_INCREMENT`.** Every primary key across all 38 models is a `String` `id`, produced one of three ways:
- `@default(uuid())` — the overwhelming majority (Prisma-generated UUID, e.g. `File.id`, `Folder.id`, `Task.id`, etc.)
- No default at all, app-generated — `User.id` (better-auth generates this before insert) and every `Token.id`-style row created through the auth library
- Explicitly client-provided UUID — `AiGeneration.id` is documented in the schema comment as "client-provided uuid (crypto.randomUUID())," used so "the gallery dedupes live items against DB rows by id"

Confirmed in `src`: `crypto.randomUUID()` / `randomUUID()` is used throughout (`src/libs/delivery-session.ts:1,23`, `src/libs/converter/video-converter.ts:16`, `src/libs/audit/metadata-collector.ts:2,44`, `src/hooks/use-template-stream-generation.ts:56-57`, `src/routes/api/generate/**`, `src/routes/api/upload/web.ts:1,186`, etc.) — reinforcing that ID generation is entirely application-side.

**Recommendation:** no `identity`/`serial` column is needed anywhere in this schema — every table's PK should be `text`/`varchar` (Drizzle: `text('id').primaryKey()`), preserving the exact current ID scheme. This question is effectively moot for this codebase, but worth stating explicitly since it rules out a whole category of migration work (no sequence reseeding, no gap-handling, no `RETURNING id` pattern changes).

## 8. Identifier casing and reserved words

Every column name in every migration is camelCase (`createdAt`, `ownerId`, `isDeleted`, ...) except a cluster of columns introduced in three later migrations that use snake_case: `nicotine_entry` (`occurred_at`, `created_at`, `updated_at`, `owner_id`) and `user.storage_quota_mib`. This is an existing inconsistency in the MariaDB schema itself, not something the Postgres migration introduces — `schema.prisma` uses `@map(...)` to reconcile the camelCase Prisma field names with the snake_case DB columns for these specific fields (e.g. `occurredAt DateTime @default(now()) @map("occurred_at")`).

**Postgres identifier folding:** per postgresql.org/docs/current/sql-syntax-lexical.html — "Key words and unquoted identifiers are case-insensitive... Quoting an identifier also makes it case-sensitive, whereas unquoted names are always folded to lower case. For example, the identifiers FOO, foo, and "foo" are considered the same by PostgreSQL, but "Foo" and "FOO" are different." This means any camelCase column (`createdAt`, `ownerId`, etc.) **must always be double-quoted** in raw SQL/psql or it silently folds to `createdat`/`ownerid` and either errors (column doesn't exist) or, worse, matches a different column if one exists. Drizzle always quotes generated identifiers, so ORM-driven code is unaffected; this is purely a risk for hand-written SQL, `psql`, admin tooling, or anyone doing a manual `\d` inspection and typing the column name unquoted.

**Reserved-word collision check** (checked all 41 table names and every distinct column name across the DDL against the official Postgres key-word appendix, postgresql.org/docs/current/sql-keywords-appendix.html): the only collision found is the **`user` table name** — `USER` is categorized as fully `reserved` in Postgres (unlike `TIMESTAMP`, `NAME`, `VALUE`, `KEY`, `ROLE`, `START`, `SESSION`, `ACTION`, `TYPE`, all of which are also used as identifiers in this schema and are all `non-reserved`, safe unquoted). `GROUP`/`ORDER` are reserved but never appear as bare column/table names here (only as substrings, e.g. `groupId`, `rbac_group`). **Consequence:** every raw-SQL reference to the `user` table must be `"user"` (quoted) in Postgres; Drizzle generates this automatically, so no functional risk through the ORM, but this is the one name in the whole schema that will error immediately if anyone writes unquoted raw SQL against it.

## 9. Charset

MariaDB `utf8mb4` is a true 4-bytes-per-character UTF-8 implementation (as opposed to MySQL's legacy 3-byte `utf8`, which this schema does not use anywhere — every table is explicitly `utf8mb4`). Postgres `UTF8` encoding is documented (postgresql.org/docs/current/multibyte.html) as 1–4 bytes per character — a full-range Unicode implementation with no distinct "3-byte" legacy mode to worry about. **Behaviour-preserving:** yes — every character storable in `utf8mb4` (including 4-byte characters: emoji, rare CJK ideographs, supplementary-plane characters) is storable identically in Postgres `UTF8`. No `latin1`/other legacy charset appears anywhere in this schema.

**Uniqueness constraints whose semantics depend on collation:** every `UNIQUE INDEX` in the DDL is on a string-typed column and therefore inherits the collation discussion from Q6 — the charset itself (byte-width) is not the issue, the *collation* attached to it is. Concretely: `user_email_key` (`user.email`), `session_token_key` (`session.token`), `token_key_key` (`token.key`), `cached_image_ownerId_hash_key`, `rbac_group_key_key`, `task_name_key`, `global_variable_name_key`, `denylist_entry_hashType_hash_key`, `file_metadata_fileId_key`, `file_rendition_paramHash_key`, `view_daily_rollup_targetKind_targetId_day_key`, `egress_rollup_ownerId_period_fileId_tokenId_rendition_key`, `template_global_variable_templateId_globalVariableId_key`, `user_group_assignment_userId_groupId_key`. Under `utf8mb4_unicode_ci`, two values differing only by case (or diacritics, in some cases under `unicode_ci`) collide today. Moving to Postgres's default case-sensitive `text` comparison relaxes every one of these constraints — rows that previously conflicted (and were rejected/deduped) will now both be allowed, most importantly for `user.email` (see Q6 duplicate-account risk) and `token.key`/`session.token` (theoretical case-variant token collision, currently prevented, would no longer be).

## Risks ranked, most dangerous first

1. **Denylist moderation-gate case sensitivity** (Q6, `src/libs/moderation/hash-gate.ts:37-41`) — a case-mismatched denylist entry silently stops blocking known-bad content after the migration. Security-relevant, silent, no error thrown.
2. **`user.email` case-sensitivity / duplicate accounts** (Q6, `src/libs/auth/auth.ts`, no email normalization found) — case-variant duplicate registrations become possible; login behaviour changes for anyone who signed up with mixed-case email.
3. **API/upload token case-sensitivity** (Q6, `src/libs/auth/token-auth.ts:8-18`) — behaviour tightens (arguably a security improvement) but is a real, silent change to what currently validates.
4. **Free-text search silently returning fewer/no results** (Q6, `files.ts:168,192`, `admin/users.ts:152`, `admin/audit.ts:90-94`, `admin/tasks.ts:388`) — no error, just degraded UX until someone notices searches "stopped working" for lowercase-vs-actual-case mismatches.
5. **`jsonb` normalization of the 28 Json columns** (Q2) — safe for this app's usage today, but silently changes stored bytes (key order, whitespace) for anything treating `audit_log.before`/`after` as an exact historical record rather than structured data.
6. **`Prisma.DbNull`/`JsonNull` conflation risk during the Drizzle rewrite** (Q2) — not currently a bug (100% of usages are `DbNull`), but a real footgun for whoever writes the Drizzle version of `prismadb.ts` if they don't know Drizzle has no equivalent sentinel.
7. **`ORDER BY name`/`email` sort-order drift** (Q6) — cosmetic, silent, depends entirely on the (currently undecided) target Postgres locale.
8. **Reserved-word `"user"` table name** (Q8) — zero risk through Drizzle/Prisma-style ORM access; real but easily-caught risk (immediate SQL error, not silent) for any hand-written SQL or admin tooling.
9. **`VARCHAR(191)` prefix-index removal** (Q5) — purely additive/simplifying change (full-column index is strictly more correct than the old prefix index), essentially no risk, listed for completeness since the question specifically asked about it.
